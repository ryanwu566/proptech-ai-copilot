## Historical proof model, PIT v3 and admission

The machine proof model stores source ID/type, publication period/instant,
retrieval instant, official URL/identifier, hash, proof class/basis and limitations.
Positive inputs must explicitly bind exact bytes to historical availability and
pass release/hash/evidence/time checks. A retrieval before the claimed availability
is inconsistent and fails closed. Existing date-only proofs use next Taipei
midnight; unqualified first-seen clocks never prove availability. A positive
machine record can enter the existing publication resolver without converting
the retrieval clock into historical publication.

These evidence objects are **reviewed attestations, not self-authenticating
signatures**. Shape/hash/Boolean validation cannot authenticate an institution.
Provider proof material must be retained and independently reviewed. This builder
supplies no real positive publication, namespace or complete-history certificate.

PIT v3 first resolves publication and full visible history at T. Proven future
events are removed before conflicts and lineage decisions. Unknown availability
prevents complete-history approval. Certificates bind dataset, exact cutoff,
visible-ledger hash and stable namespace, complete revision/cancellation history
and replacement links; each fold freeze requires its own certificate.

After version selection, the selector checks the frozen Target B contract,
strict no-parking treatment and required external source dependencies. The list
must be explicit, including an explicit empty list when no external supplement
is used. Each dependency binds its ID/hash to qualified availability by T.
Embedded schemas/details depend on the exact archive and existing joins/hashes.
Checking dependencies after supersession prevents an unavailable correction
supplement from resurrecting the old version. Duplicate versions with conflicting
dependencies are quarantined. Source/target/feature fields remain confined to
existing non-personal research inputs and public aggregate privacy filters.

ML-B Admission Gate v1 requires the entire conjunction: nonempty approved cohort,
sufficient historical proof, lineage, stable namespace, exclusion of temporal
leakage, chronological coverage, deterministic rebuild, privacy and frozen target
contract. No partial result authorizes training. The builder leaves rebuild
certification pending; external comparison and final validation record that
condition after two clean builds. Lack of complete history fails the leakage
assurance condition, without claiming a specific leaked row was found.
